Acceptance and review criteria

Current documentation acceptance

The pack should make Type Rave understandable as a distinct graphic instrument. Reviewers must be able to explain what the visitor writes, what they manipulate, and what they can preserve as an output. The three behavior descriptions should differ in composition, not merely in color or speed. The current reference image must remain labeled as existing DIA artwork.

Each document should have a clear role. Product defines purpose and boundaries; Experience explains the first minute; Visual direction establishes the graphic vocabulary; States explains recovery; Assets identifies what is delivered and missing; Technical plan records future options. The package should not imply that microphone capture, typography rendering, or export has been implemented.

Graphic approval

A later screen-art review should examine a stable resting frame, a moderate motion frame, a peak, and a frozen result for each behavior. The phrase must be legible at rest. Peak distortion should still reveal an intentional relationship to the same words. Negative space, alignment, and counter shapes matter more than the quantity of shader effects.

The bottom strip should remain shallow and readable. No permanent sidebar should reduce the stage. A phone study should show usable text editing and reachable freeze/save actions. The viewer should not have to guess whether a frame is intentionally frozen, silent, or broken.

Interaction approval

The proposed phrase must survive behavior and source changes. Keyboard shortcuts must be suspended while typing. Reset must not unexpectedly erase the visitor's words. Microphone denial, silence, and unavailable hardware need distinct explanations with a usable fallback. A live indicator must accurately reflect capture state in any future implementation.

Reviewers should choose the default phrase, font, palette, motion intensity, and audio source before detailed production. They should also decide whether local-file audio and project saving belong in the first version. Those decisions must not be silently added because they are technically possible.

Future functional acceptance

If development is authorized later, tests should cover text bounds, stable line breaks, mapping limits, source switching, freeze consistency, and export dimensions. A saved project should reopen with the same font and defined layout rules. Device tests should examine touch reach, keyboard focus, reduced motion, and high-energy input.

Use WCAG 2.2 as an accessibility reference and review the actual rendered behavior rather than declaring conformance from static art. No current performance, usability, or accessibility result is claimed. Concept acceptance means the direction and remaining choices are clear enough for an informed next decision.
